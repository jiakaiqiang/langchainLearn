# 05 Tools

## 这一章学什么

这一章对应 LangChain 官方文档里的 **Tools**。如果说前几章都还停留在“模型如何理解上下文、如何返回结果”，那么从这一章开始，模型第一次真正获得了**接触外部世界的能力**。

Tool 不只是“一个函数”这么简单。更准确地说，它是：**应用在受控边界内暴露给模型使用的能力接口。**

模型本身擅长理解语言、组织回答、做推理，但它并不知道你的内部系统、数据库、接口文档、业务规则或实时状态。只有当你把这些能力包成 tool 并授权给模型时，模型才有可能在回答过程中真正获取信息、执行动作或调用系统能力。

这也是现代 LangChain 官方文档为什么会非常强调 tools：它是从“会说话的模型”走向“能完成任务的应用”的关键分界线。

## 本章核心概念

### 1. Tool 是受控能力暴露，不是任意执行入口

很多人第一次看到 tool calling，会误以为它就是“模型可以随便调用函数”。这会带来很危险的理解偏差。正确理解应该是：

- 应用决定暴露哪些能力
- 每个能力有明确名称、描述、参数 schema、返回边界
- 模型只能在这些受控接口内做选择
- 真正执行动作的仍然是你的应用代码，不是模型本身

也就是说，tool 是**应用授予模型的能力边界**，不是把系统权限无条件交出去。

### 2. name / description / schema / return shape 都很重要

一个 tool 的效果好不好，往往取决于这几个元素是否清晰。

#### 名称 `name`

名称要让模型容易区分这个工具的用途。含糊的名字会让模型更难正确选择。

#### 描述 `description`

描述实际上是在告诉模型：

- 什么时候该用这个工具
- 什么时候不该用
- 输入是什么语义
- 返回结果适合用来做什么

从某种角度看，tool description 也是一种 prompt，但它作用于“工具选择”这件事。

#### 参数 schema

schema 决定模型调用工具时必须提供哪些字段、每个字段是什么类型、允许哪些输入范围。这是控制错误调用和提升稳定性的关键。

#### 返回 shape

虽然很多 demo 里 tool 只是返回一段字符串，但真实应用里你同样要关心返回值的结构是否稳定，因为它会进入后续模型推理或应用逻辑。

### 3. Tool calling lifecycle

这一章必须建立一个完整运行时心智模型：

1. 用户提出问题
2. 模型判断是否需要工具
3. 模型生成一个工具调用意图
4. 应用执行真正的工具代码
5. 工具结果返回给模型
6. 模型基于工具结果组织最终回答

所以工具调用并不是“模型自己执行了函数”，而是“模型提出调用请求，应用代为执行，再把结果喂回模型”。

### 4. 工具不只用于查数据

Tool 可以是：

- 查询组件文档
- 查询接口定义
- 查天气
- 查订单状态
- 保存用户偏好
- 触发工作流
- 调用内部 API

也就是说，tool 既可以是 read-only 能力，也可以是带副作用的 action 能力。副作用一出现，安全边界就更重要。

## 先看本仓库里的代码锚点

这一章对应的本地代码是：

- `src/demos/05-tools/index.ts`

### 为什么先看这段：工具本体是怎样被定义出来的

```ts
const getComponentDoc = tool(
  async ({ component }) => {
    const docs: Record<string, string> = {
      Table: "Table 组件适合展示分页数据，常见能力包括 columns、rowKey 和 loading。",
      Modal: "Modal 组件适合承载确认、编辑和详情查看流程，注意控制打开状态和关闭回调。",
      Form: "Form 组件适合处理受控输入、校验规则和提交动作。",
    };

    return docs[component] ?? `${component} 组件暂无示例文档，请先补充设计系统说明。`;
  },
  {
    name: "get_component_doc",
    description: "查询前端组件的简要文档说明",
    schema: z.object({
      component: z.string().describe("组件名称，例如 Table、Modal、Form"),
    }),
  }
);
```

这段代码处在本章流程的**能力暴露层**。应用把一个本地查询能力包装成了一个可被模型理解和选择的 tool。

它对应的是官方文档里的 **tool definition**：不仅有执行逻辑，还有 `name`、`description`、`schema` 这些让模型知道“什么时候该调、怎么调”的元信息。

这里刻意简化的是：当前 tool 只做只读查询，而且返回值是简单字符串。真实工具系统里常常还要考虑结构化返回、错误语义、权限校验和副作用控制。

### 为什么再看这段：工具不是单独存在，而是被挂进 agent 的能力集合

```ts
const agent = createAgent({
  model: createDemoModel(),
  tools: [getComponentDoc],
});
```

这段代码处在**能力注册层**。它说明 tool 定义好之后，并不会自动生效，而是要显式挂进 agent，成为模型可调用能力的一部分。

它对应的是官方语境里的 **tool-enabled agent runtime**：模型不是天然知道你的系统能力，而是应用在运行时把能力边界授予它。

这里刻意简化的是：当前 demo 只有一个工具，因此不存在多工具选择歧义。真实应用里工具一多，name、description、schema 的质量会直接影响模型选得准不准。

### 为什么最后看这段：工具调用路径是“模型决定，应用执行”

```ts
const result = await agent.invoke({
  messages: [
    {
      role: "user",
      content: "请先查询 Table 的组件说明，再告诉我它适合什么场景。",
    },
  ],
});

console.log(result.messages.at(-1)?.content);
```

这段代码处在**实际运行层**。用户并没有手动调用 `getComponentDoc`，而是把任务交给 agent，再由模型决定是否需要先查组件文档。

它对应的是官方文档里的 **tool-calling lifecycle**：模型生成调用意图，应用执行工具，再把结果送回模型继续推理。

这里刻意简化的是：当前 demo 只输出最终消息，没有把中间的 tool call、tool result、消息流转细节单独展示出来。但这条最小链路已经足够帮助你建立正确心智模型。

## 关键 API / 运行时形态

### `tool(...)`

LangChain 里常见的工具定义方式。你会给它提供：

- 具体执行逻辑
- 工具名称
- 描述
- `zod` schema 等输入约束

### 模型提出调用，应用执行调用

这是最重要的运行时形态。tool 并不是你手动先执行好再喂给模型，而是模型根据语境决定是否要调，然后应用再执行。

### 工具结果重新进入消息流

工具返回的数据通常会重新进入模型上下文。于是模型可以把“自己本来不知道的信息”纳入回答过程。这正是 tool 对 agent 的基础意义。

## 前端接入时要注意什么

### 1. 浏览器侧工具和服务端工具要区分

很多工具并不适合直接暴露在浏览器侧，例如：

- 访问私有数据库
- 调用内部管理接口
- 写入持久化存储
- 触发带副作用的业务动作

前端可以发起请求，但工具真正执行通常更适合放在服务端或边缘层。否则你会很快遇到权限、密钥、安全和审计问题。

### 2. 工具描述会直接影响选择质量

很多工具“调不准”的原因，不是模型太笨，而是 name / description / schema 写得太模糊。当前端项目里工具越来越多时，这一点会尤为明显。

### 3. 带副作用的工具必须考虑幂等与确认

如果工具会：

- 下单
- 发消息
- 删除数据
- 修改配置

那么你必须额外考虑：

- 是否需要用户确认
- 是否要求幂等
- 是否能重试
- 是否需要审计日志

这已经超出了“演示能跑就行”的范畴，进入产品安全边界。

### 4. 工具结果不应盲目信任为最终真相

工具只是数据来源之一。你仍然要考虑：

- 返回是否为空
- 返回是否过期
- 返回是否过长
- 返回是否需要再次过滤或摘要

否则模型可能会把噪音也当成高权重上下文。

## 这一章没有展开的能力，其实是什么

### 1. Tool metadata 为什么这么重要

很多人会把 `name`、`description`、`schema` 当成附属信息，但在真实运行时它们非常关键，因为模型是靠这些信息判断：

- 什么时候该调这个工具
- 要填什么参数
- 调回来之后能得到什么

也就是说，tool metadata 本身就是运行时控制的一部分。

### 2. 只读工具和带副作用工具是两类问题

教学 demo 选择的是查文档工具，因为它最安全、最容易理解。但真实工程里，查数据和做动作是两类完全不同的问题：

- 查数据更关注召回、格式、时效性
- 做动作更关注确认、幂等、审计、权限

本仓库先从 read-only tool 入手，是为了先把生命周期讲清楚。

### 3. Server-side tool use 为什么重要

官方文档会继续强调 server-side tool use，是因为很多真实工具都必须放在受控环境里执行：

- 带密钥的内部 API
- 私有数据库
- 需要权限校验的业务写操作
- 需要审计的系统动作

前端通常负责触发和展示状态，而不应该直接承担敏感工具执行逻辑。

## 能力边界与 tradeoff

### 什么时候用 Tool 很合适

- 模型本身不知道答案
- 需要实时数据或内部资料
- 需要访问应用能力
- 需要做受控动作执行

### 什么时候不该先上 Tool

- 单纯语言改写
- 单步文本生成
- 根本不存在外部依赖
- 任务本身不需要调用系统能力

### 主要 tradeoff

- 加入工具后，能力更强，但运行时更复杂
- 工具越多，能力越丰富，但选择歧义也可能增加
- 带副作用工具越多，安全和确认机制越重要

## 与下一章的关系

当你理解了 tool 的运行时闭环之后，下一步自然会进入 Agent：

- tool 只是能力集合
- agent 才负责在上下文里决定何时调用哪个工具、调用几次、调用后如何继续

所以 tools 是 agent 的基础，而 agent 是 tools 的调度者。
